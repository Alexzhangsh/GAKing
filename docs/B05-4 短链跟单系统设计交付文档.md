# B05-4 短链跟单系统交付文档

## 一、数据表设计

### 1.1 short_link（短链映射表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| short_key | VARCHAR(32) | UNIQUE, NOT NULL | 短链唯一标识（base62 编码，8位） |
| user_id | BIGINT | NOT NULL | 用户ID |
| goods_id | VARCHAR(128) | NOT NULL | 商品ID |
| goods_title | VARCHAR(256) | DEFAULT '' | 商品标题 |
| channel_code | VARCHAR(32) | DEFAULT '' | 渠道标识（myq/orderx/dta） |
| source_url | TEXT | DEFAULT '' | 原始CPS推广链接 |
| expire_at | DATETIME | NOT NULL | 过期时间（生成时间 + 72h） |
| click_count | INT | DEFAULT 0 | 累计点击次数 |
| last_click_at | DATETIME | NULL | 最后点击时间 |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | DEFAULT CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| is_delete | BOOLEAN | DEFAULT FALSE | 软删除标记 |

**索引设计：**
- `idx_short_key` — UNIQUE，短链key查询
- `idx_user_id` — 用户维度的短链列表查询
- `idx_goods_id` — 商品维度的短链列表查询
- `idx_expire_at` — 过期短链的批量清理

**核心逻辑：** 短链 key 采用 base62 编码（数字+小写字母+大写字母），8位长度提供 62⁸ ≈ 218 万亿组合空间。生成时使用`时间戳毫秒 + 随机数`作为随机种子，碰撞概率极低，且内置 5 次重试 + 扩展长度兜底机制。

### 1.2 click_log（点击行为日志表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| short_key | VARCHAR(32) | NOT NULL | 关联短链key |
| user_id | BIGINT | NOT NULL | 用户ID |
| goods_id | VARCHAR(128) | NOT NULL | 商品ID |
| goods_title | VARCHAR(256) | DEFAULT '' | 商品标题 |
| source_channel | VARCHAR(32) | DEFAULT '' | 来源渠道 |
| user_agent | VARCHAR(512) | DEFAULT '' | User-Agent |
| ip_address | VARCHAR(64) | DEFAULT '' | IP地址 |
| referer_url | VARCHAR(1024) | DEFAULT '' | 来源URL |
| access_time | DATETIME | NOT NULL | 访问时间 |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | DEFAULT CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| is_delete | BOOLEAN | DEFAULT FALSE | 软删除标记 |

**索引设计：**
- `idx_short_key` — 短链维度的点击查询
- `idx_user_id` — 用户维度的点击历史
- `idx_goods_id` — 商品维度的点击查询
- `idx_access_time` — 时间维度的查询/清理
- `idx_goods_access` — 联合索引：`(goods_id, access_time)`，**核心匹配查询索引**

**核心逻辑：** 每张表记录一次短链重定向的点击行为。`goods_id + access_time` 联合索引是跟单匹配的关键查询路径，用于在 72h 窗口内按商品ID查找点击记录。

**索引设计：**
- `idx_out_order_no` — UNIQUE，查重防重复入库
- `idx_review_status` — 按复核状态筛选
- `idx_channel_code` — 按渠道筛选
- `idx_create_time` — 按创建时间排序

**复核状态枚举：**
| 状态值 | 含义 | 说明 |

| PENDING | 待审核 | 默认状态，尚未处理 |
| REVIEWED | 已复核 | 运营人工确认无法归属，订单已纳入异常 |
| IGNORED | 已忽略 | 运营确认无需关注（如测试订单、重复数据） |

## 二、完整匹配规则说明

### 2.1 整体匹配流程

```
CPS订单同步
     │
     ▼
┌─────────────────────────────────────┐
│         AttributionEngine           │
│         （跟单引擎）                  │
│                                     │
│  策略链（按优先级依次尝试）：           │
│  ① ShortLinkAttributionStrategy     │
│     （短链+点击日志，默认模式）        │
│  ② RelationIdAttributionStrategy    │
│     （relation-id，预留模式）         │
│                                     │
│  任一策略匹配成功 → 返回 user_id      │
│  全部策略未匹配   → 触发异常订单入库   │
└─────────────────────────────────────┘
     │                    │
     ▼                    ▼
 订单归属用户         异常订单库
（写入orders表）   （人工复核流程）
```

### 2.2 72小时 Last-Click 匹配规则

**窗口期定义：** 以订单支付时间为基准，向前回溯 72 小时。若订单暂未支付（订单状态为"已下单"），则以当前时间为基准。72h 窗口与短链过期时间一致，确保短链有效期与匹配窗口完全对齐。

**匹配算法步骤：**

```
Step 1: 输入参数
  └─ goods_id（商品ID，必填）
  └─ channel_code（渠道标识，可选过滤）
  └─ pay_time（支付时间，用于精确窗口计算）

Step 2: 查询 ClickLog
  └─ SELECT * FROM click_log
     WHERE goods_id = :goods_id
       AND access_time >= NOW() - 72h
       [AND source_channel = :channel_code]
     ORDER BY access_time DESC

Step 3: 判定逻辑
  ├─ 无点击记录 → 匹配失败（异常原因：72h窗口内无匹配点击记录）
  ├─ 有点击记录 →
  │   ├─ 取第1条（access_time最新）→ 确定用户
  │   ├─ 检查是否多用户（unique_users > 1）
  │   │   ├─ 否 → 高置信度匹配（confidence=0.9）
  │   │   └─ 是 → 低置信度匹配（confidence=0.5），
  │   │           附加异常原因标记
  │   └─ 返回 MatchResult
  └─
```

**匹配置信度：**
| 场景 | 置信度 | 说明 |
|------|--------|------|
| 单用户点击 | 0.9 | 只有1个用户点击过该商品，归属确定 |
| 多用户点击 | 0.5 | 多个用户点击过，取最新一次，但存在不确定性 |
| 无点击记录 | 0.0 | 匹配失败，进入异常订单库 |

### 2.3 策略架构设计

```
BaseAttributionStrategy（抽象基类）
        │
        ├── ShortLinkAttributionStrategy（默认策略）
        │     └── 通过 ClickLogDAO 查询点击日志
        │     └── 实现 72h last-click 匹配逻辑
        │     └── 返回 MatchResult（含置信度）
        │
        └── RelationIdAttributionStrategy（预留策略）
              └── 当前返回未匹配（占位实现）
              └── 未来通过 relation_id → user_id 映射匹配
              └── 启用条件：渠道升级为渠道-分销类型推广位
```

**策略切换机制：** `AttributionEngine.set_strategies()` 支持运行时替换整个策略链，无需修改业务代码即可从 `short_link` 模式切换到 `relation_id` 模式。

### 2.4 匹配规则场景示例

| 场景 | 点击记录 | 匹配结果 | 后续处理 |
|------|----------|----------|----------|
| 用户A点击商品X，5h后下单 | 1条（user_id=A） | 匹配到A，confidence=0.9 | 订单正常归属A |
| 用户A/B/C先后点击商品X，C最后 | 3条（A→B→C） | 匹配到C，confidence=0.5 | 归属C，标记多用户 |
| 用户A点击商品X，4天后才下单 | 已过期（>72h） | 匹配失败 | 入库异常订单 |
| 订单商品ID无任何点击记录 | 0条 | 匹配失败 | 入库异常订单 |
| 商品ID为空 | — | 直接返回失败 | 入库异常订单 |

## 三、异常订单处理逻辑

### 3.1 异常订单入库条件

以下任一条件满足时，订单自动存入 `abnormal_order` 表：

1. **无点击记录（ABNORMAL_REASON_NO_CLICK）**
   - 72h 窗口内，该商品ID没有任何点击记录
   - 典型场景：用户未通过平台短链购买、订单同步时短链已过期

2. **多用户冲突（ABNORMAL_REASON_MULTI_USER）**
   - 72h 窗口内，存在多个不同用户的点击记录
   - 虽然取最后一位用户作为归属，但低置信度仍需人工复核
   - 典型场景：多个用户分享了同一商品链接

3. **短链已过期（ABNORMAL_REASON_CLICK_EXPIRED）**
   - 短链存在但已超过 72h 有效期
   - 典型场景：用户点击后长时间未下单

### 3.2 入库数据完整性

异常订单入库时，会同步保存以下关键信息，确保运营可完整追溯：

- **原始订单快照：** `order_data` 字段保存渠道返回的完整 JSON 数据
- **匹配尝试记录：** `matched_click_key` 记录最近一次匹配的短链key，`matched_user_id` 记录可能属于的用户ID
- **业务信息：** 支付金额、佣金、商品信息等，便于运营判断是否需人工找回

### 3.3 去重保障

入库前按 `out_order_no` 查重，已存在的异常订单不会重复插入（幂等设计）。同一渠道订单号在 `abnormal_order` 表中唯一。

### 3.4 人工复核流程

```
┌────────────────────────────────┐
│    异常订单入库（PENDING）       │
│    运营登录后台查看列表           │
└────────────────────────────────┘
              │
              ▼
┌────────────────────────────────┐
│    运营人工核查订单详情           │
│    ┌─ 查看原始订单数据           │
│    └─ 查看匹配尝试记录           │
└────────────────────────────────┘
              │
              ▼
┌────────────────────────────────────────────┐
│            复核决策                          │
│                                            │
│  ┌────────────────┐  ┌────────────────┐    │
│  │  REVIEWED       │  │  IGNORED       │    │
│  │（已复核）        │  │（已忽略）       │    │
│  ├────────────────┤  ├────────────────┤    │
│  │ 确认无法归属     │  │ 测试/重复订单   │    │
│  │ 记录为最终异常   │  │ 无需关注       │    │
│  └────────────────┘  └────────────────┘    │
└────────────────────────────────────────────┘
              │
              ▼
┌────────────────────────────────┐
│    复核记录持久化                │
│    └─ review_status            │
│    └─ review_remark            │
│    └─ reviewed_by（管理员ID）   │
│    └─ reviewed_at（复核时间）    │
└────────────────────────────────┘
```

### 3.5 后台管理接口

| 接口 | 方法 | 路由 | 说明 |
|------|------|------|------|
| 异常订单列表 | GET | `/api/v1/admin/abnormal-orders/list` | 分页查询，支持复核状态、渠道、关键词筛选 |
| 复核异常订单 | PUT | `/api/v1/admin/abnormal-orders/{id}/review` | 标记为 REVIEWED 或 IGNORED |
| 异常订单统计 | GET | `/api/v1/admin/abnormal-orders/stats` | 返回各复核状态的数量统计 |

**后台页面功能：**
- 统计概览卡片：异常订单总数、待审核数、已复核数、已忽略数
- 多条件筛选：关键词（订单号/商品标题）、渠道、复核状态
- 分页表格：展示关键字段（订单号、商品、金额、佣金、异常原因、复核状态）
- 复核弹窗：展示订单详情、异常原因，支持选择复核结果 + 填写备注
- 权限控制：挂载 `order:manage` 权限点，纳入 RBAC 体系

### 3.6 数据生命周期

- **短链数据：** 72h 过期后不再接受点击，但保留记录供归档查询。建议按周清理过期且无点击的短链记录。
- **点击日志：** 保留 30 天，超期数据可归档或清理（72h 窗口期外的数据对跟单匹配无意义）。
- **异常订单：** 永久保留，运营复核后不可删除，有助于后续分析异常原因和优化匹配规则。
